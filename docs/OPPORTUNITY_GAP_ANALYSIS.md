# 麦当劳 MCP 全量 Issue 调研：遗漏机会分析

> 调研时间：2026-10-25 08:23–08:40（北京时间）
> 数据源：`M-China/mcd-developer-innovation-challenge` 公开 GitHub Issues API 与单条 Issue 搜索结果。
> 样本：通过 REST API 分页抓取第 1–10 页，得到 999 条不含 Pull Request 的公开 Issue（API 分页在第 10 页后返回 422；官方网页当时显示全量约 1207 条，故以下是高覆盖样本而非绝对全量）。

## 一、最重要的判断

### 不建议继续做的“表面创新”

以下方向在样本中已经明显拥挤：

- 通用一句话点餐 / 套餐推荐；
- 省钱、查券、凑单、满减和预算优化；
- 热量、蛋白质、低脂、低钠和减脂；
- 多人拼单、团餐、AA 分账；
- 人格测试、小游戏、分享卡；
- 渠道比价、到店/外送/得来速选择；
- 会员、积分、早餐卡和优惠券资产管理。

关键词统计存在重叠，不能直接相加，但足以说明方向密度：

| 主题 | 999 条样本中命中的 Issue 数 |
|---|---:|
| 省钱 / 优惠 / 凑单 | 695 |
| 营养 / 热量 / 减脂 | 396 |
| 通用点餐 / 推荐 | 391 |
| 多人 / 聚餐 / AA | 262 |
| 游戏 / 人格 / 内容 | 233 |
| 工程 / 测试 / 数据 | 276 |
| 场景化人群 | 164 |
| 会员 / 资产 | 208 |

这些数字按标题和简介关键词统计，主题可以重叠，适合用于方向密度判断，不是官方分类或获奖预测。

## 二、被覆盖较少的机会

### 机会 A：餐后“到货核对 + 异常处理”

已有一个非常明确的作品：

- [#756 麦麦到货核对官](https://github.com/M-China/mcd-developer-innovation-challenge/issues/756)

它已经覆盖订单与实际收到餐品的核对，但简介明确保持“只生成沟通草稿，不自动退款、不自动联系商家”。全量样本中，售后、退款、缺货、漏餐、配送异常不是主流方向。

可挖掘的空白不是简单重复“核对餐品”，而是：

- 用订单结构自动拆解“套餐缺哪一层”；
- 区分没拍到、没确认、疑似缺失和确定缺失；
- 给出最小证据清单；
- 生成不带攻击性的客服沟通草稿；
- 记录一次异常，影响下一次渠道/门店选择。

**适合度：高。** 真实痛点强，MCP 的订单读取能力有用，且和现有“点餐前推荐”形成完整闭环。

### 机会 B：餐品“可获得性 / 备选计划 / 缺货恢复”

已有 [#452 麦门备选计划](https://github.com/M-China/mcd-developer-innovation-challenge/issues/452)，但这个方向仍有进一步空间：

- 目标餐品在当前门店不可用时，寻找“口味/营养/价格”最接近的替代；
- 分辨“本店没上架”“渠道不售”“时段不可用”“真实售罄”；
- 对固定不可替换品保留硬约束；
- 计算换餐后对券、套餐轮次和能量的连锁影响；
- 输出“保留原目标 / 保预算 / 保能量 / 保口味”的不同恢复路径。

**适合度：高。** 这是比普通推荐更像“故障恢复”的产品，演示时容易讲清楚。

### 机会 C：无障碍的“跨人交接”

无障碍方向已有多件作品：

- [#749 麦声](https://github.com/M-China/mcd-developer-innovation-challenge/issues/749)
- [#562 适老与无障碍点餐台](https://github.com/M-China/mcd-developer-innovation-challenge/issues/562)
- [#529 麦麦长辈模式](https://github.com/M-China/mcd-developer-innovation-challenge/issues/529)
- [#498 麦麦无障碍点餐](https://github.com/M-China/mcd-developer-innovation-challenge/issues/498)

因此“再做一个大字版点餐”不够独特，但还存在一个未被充分凸显的场景：

> 子女/同事帮助长辈或低视力用户点餐时，如何把推荐、替换、差价和最终确认交接清楚？

可以做成“代点交接卡”：

- 适老化大字、语音朗读和一问一答；
- 每一步标记“谁做决定”；
- 把不确定的营养或过敏信息显式标红；
- 生成可转发给长辈确认的卡片；
- 不把代点人默认当成最终确认人。

**适合度：中高。** 需要避免与已有无障碍项目正面重复，应突出“跨人确认与责任交接”。

### 机会 D：饮食安全的“未知项管理”

过敏、素食、清真、忌口已经有作品：

- [#1158 麦麦安心点单官](https://github.com/M-China/mcd-developer-innovation-challenge/issues/1158)
- [#1107 麦麦忌口管家](https://github.com/M-China/mcd-developer-innovation-challenge/issues/1107)
- [#699 McHealth Agent](https://github.com/M-China/mcd-developer-innovation-challenge/issues/699)
- [#1187 麦麦家庭点餐助手](https://github.com/M-China/mcd-developer-innovation-challenge/issues/1187)

机会不在“再做一个忌口过滤器”，而在于把安全等级和证据链做得更严格：

- 安全可选；
- 去除某项后可选；
- 需要到店确认；
- 信息不足，禁止推荐；
- 可能存在交叉接触，不能保证无过敏原。

**适合度：中。** 价值很高，但要避免医疗化表述，并且必须依赖可信的成分/过敏原数据；MCP 本身字段不足时不能硬推断。

### 机会 E：点餐“时间可靠性”而非单纯时段推荐

已有：

- [#1167 麦门末班车](https://github.com/M-China/mcd-developer-innovation-challenge/issues/1167)
- [#1117 麦麦空档](https://github.com/M-China/mcd-developer-innovation-challenge/issues/1117)
- [#822 麦麦课间窗口](https://github.com/M-China/mcd-developer-innovation-challenge/issues/822)
- [#503 麦麦 JIT 零等待通勤取餐助手](https://github.com/M-China/mcd-developer-innovation-challenge/issues/503)
- [#365 麦麦落地补给](https://github.com/xm6661885/mcd-arrival-meal/issues/365)

因此“我还有 30 分钟能不能吃到”并非空白。可以继续向“延误后的恢复策略”发展：

- 出餐慢、门店关闭、预约时段变化时怎么办；
- 迟到后是取消、改店、换餐还是继续等；
- 把时间损失和价格/能量损失放到同一张决策表；
- 对外送、到店、得来速做“成功到手概率”而非只比较名义时间。

**适合度：中高。** 需要真实等待时长/营业状态数据支撑。

### 机会 F：食物浪费的“买前可避免性”

样本中出现过：

- [#848 麦麦健身餐规划师](https://github.com/linzhiqin2003/mcfit-meal-planner/issues/848) 提到分顿吃和减少浪费；
- [#545 麦麦碳账本](https://github.com/yeqv111/mccarbon/issues/545) 关注碳足迹；
- [#452 麦门备选计划](https://github.com/dusensen000/mcd-where-to-buy/issues/452) 关注餐品可获得性。

但“避免点多 / 避免不吃的配菜 / 复热或分顿 / 适合分享的份量”仍没有像省钱和热量一样成为主产品。

可以做：

- 根据人数、食量、用餐时长和是否分享计算“刚好够”；
- 识别用户明确不吃的配菜，避免因为套餐优惠被迫购买；
- 区分“价格更低”与“实际浪费更少”；
- 在推荐结果中显示“预计剩余风险”，而不编造碳排数字。

**适合度：中高。** 叙事清晰，能与麦有数的复盘功能自然结合。

## 三、我认为最值得押注的路线

### 主路线：麦有数，点餐推荐与反事实复盘

作品统一名为“麦有数”，将方案生成与复盘组成以下流程：

```text
现在怎么点
→ 真实核价
→ 只改一个变量的反事实比较
→ 识别最可能的后悔来源
→ 生成下一次点餐协议
```

它的优势：

- 不与“省钱/营养/点餐助手”正面竞争；
- 能复用已有 MCP 调用链；
- 具有可演示的视觉化结果；
- 既能讲产品价值，也能讲工程确定性；
- 有机会连接餐后订单复盘、缺货备选、时间恢复和减少浪费。

### 扩展功能：餐品不可用时的恢复方案

如果要再增加一个真正能拉开差异的功能，我建议不是继续加更多优惠，而是增加：

> **目标餐品不可得时，按“保口味 / 保预算 / 保能量 / 保到手时间”四种目标恢复方案。**

这个功能比静态备选推荐更有故事：用户不是重新面对 100 个餐品，而是告诉系统“我最不想牺牲什么”。

## 四、不建议押注的方向

- 再做一个普通三套套餐推荐器；
- 再做一个券包扫描 + 凑单工具；
- 再做一个低卡/高蛋白推荐器；
- 再做一个多人 AA 工具；
- 再做一个简单人格测试或分享海报；
- 再做一个只改变配色的点餐页面。

## 五、建议的下一步 MVP

1. 结果页继续保留“现在怎么点 / 如果已经点过”双模式；
2. 增加一个输入：`我最不想牺牲什么？价格 / 口味 / 能量 / 到手时间`；
3. 增加一个“餐品不可用时怎么办？”入口；
4. 用实时 MCP 重新核验 3 个反事实方案；
5. 输出一张“后悔成本卡”：
   - 多花多少钱；
   - 多了多少能量；
   - 少了哪张真实可用券；
   - 是否导致等待/渠道变化；
   - 下一次的一条规则；
6. 正式作品名统一为 **麦有数**，宣传语为“点前算清，点后有数”。推荐与复盘作为功能入口，不再叠加其他品牌名。
