## 解析流程

1. 检查 data 类型。若为结构化数组则按其字段解析；若为字符串则识别 `[N]{字段名,...}:` 表头和后续缩进行。不得对 TOON 直接执行 JSON.parse 或 json.loads。
2. 按表头映射每列，验证实际行数与 N、每行列数与字段数。不写死能量所在列；字段顺序变化时重新映射。
3. 对实测无引号、无嵌入逗号的行，可按逗号分列。出现带引号、转义、逗号或换行的复杂单元格时使用宿主已有的合规 TOON/CSV 解析能力；不能盲目 split 后错位计算。无可靠解析能力时标为解析失败，不臆造数据。
4. 将数值列转为数值，将字面 null、空白、非法数值保留为未知。nutritionDescription=null 只是文字描述缺失，不表示该行 energyKcal 缺失。
5. 用 energyKcal 显示 kcal（大卡），energyKj 为 kJ，不混用。若只返回 kJ，允许以 kcal=kJ/4.184 换算并明确“换算参考”，不覆盖已有 kcal。营养表其余数值按官方字段的单位说明呈现；未核实单位时不擅加单位作硬约束。
6. 匹配具体餐品名称、份量、冷热和规格。允许解释明确的同义名，如“纯牛奶(盒装)”与“纯牛奶（盒装）”；不把“牛奶”自动映射为任意杯型。优先从套餐详情的子项名匹配，不只用菜单聚合商品名“可乐/薯条”。
7. 对重复行检查营养数值是否一致。一致时按同一标准份记录使用一次；不一致时标记冲突，不能重复相加或选择有利值。
8. 按每份子项数量和套餐数量相乘后相加。使用套餐整体营养或子项合计中的一种，不能重复计入。

## 未知不是0

- 未匹配、新品、特调后无营养、杯型不明、null、解析失败都标未知。输出“已知部分合计 X kcal，另有 Y 项未知；总热量未核实”，不输出完整总值或声称满足上限。
- 只有官方明确给出数值0才可计0，例如本次无糖可口可乐中杯 energyKcal=0；不能由“无糖”推断所有营养都是0，实测仍有碳水和钠字段。
- 去冰、加冰、去酱、加料不能靠经验扣减能量。若标准份营养仍可作为参考，标明“标准份参考，未覆盖特调”，不据此确认特调方案满足严格热量限制。
- 不能把营养库存在某条记录视为当前门店可售证明；先核验菜单/套餐详情。

## 张江案例算术自检

- 默认：板烧391 + 中薯289 + 中杯可乐147 = 827 kcal。
- 只换饮料：板烧391 + 中薯289 + 无糖中杯0 = 680 kcal；差值680-827=-147 kcal。
- 只换小食：板烧391 + 小杯玉米53 + 中杯可乐147 = 591 kcal；差值591-827=-236 kcal。

这些是官方标准份条目的合计参考，均不是用户实际摄入测量值；运行时须重新查询。
